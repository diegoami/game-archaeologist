# T07 A record validator game repositories can call (#10, ADR-009)

- **Kind**: infrastructure
- **Issue**: #10 · **Branch**: `task/T07-validate-records` · **Merge after**: T06
- **Implementer**: opencode (`deepseek-flash`): **hard** (rule 20: a guard task, record integrity,
  and a new mechanism that several repositories call) · **Claude fallback**: opus. **Round 3: claude
  (opus)**, escalated by the owner on 2026-10-04. Rounds 1 and 2 each had one blocking finding of the
  same class (malformed input crashes the validator), so the fix did not converge (`docs/models.md`,
  escalating the implementer)
- **Reviewer**: opencode (`gpt-6.1-sol`, variant low); never the implementer's family. **Guard
  task**: this validator decides which run records and manifests are valid in every game
  repository, so a defect lets a corrupt record pass as evidence.
- **Why**: ADR-009 moves code here when a second consumer copies it. Three already do. Today game
  repositories validate records with code that this repository treats as a test script.
- **Evidence** (re-checked on `main` at e201e48, 2026-10-04):
  - **toy-archaeology and goal2-archaeology:** each carries a near-identical `tools/ga.py`. It fetches
    `tests/formats/check_examples.py` at the commit `archaeology.json` pins, and imports
    `validate`, `semantic_errors` and `canonical_set_hash` from it.
  - **isle-wars-archaeology:** it vendored `tests/formats/check_examples.py` into its own tree
    (`tools/register_artifact.py:35`). Below `def validate`, its copy already differs from ours.
  - **The cost:** an earlier contract checked only the canonical id, and an invalid manifest merged
    (diegoami/toy-target#3: `acquired.when` was a timestamp).
  - **`tests/formats/check_examples.py`** (178 lines, stdlib only) holds:
    - the keyword whitelist (`KEYWORDS`, `unknown_keywords`);
    - the validator (`validate`);
    - the two rules no schema can express (`canonical_set_hash`, `semantic_errors`);
    - this repository's own checks: the examples against `formats/examples/expected-errors.json`,
      and the claim statuses of `vocabulary/status.md` against 06 §4.
  - **Mapping:** a document names its format in its top-level `schema` field (`artifact-set/1`,
    `run/1`, …), which equals the `$id` of `formats/<name>-<v>.schema.json`.
- **Owns**: `tools/validate_records.py`, `tests/formats/**`, `formats/README.md`,
  `.github/workflows/ci.yml`
- **Scope**:
  - **Protects:** record validity in every game repository. The validator must never let any of
    these through: an invalid record or manifest reported `ok` (exit 0); a valid one rejected; a
    traceback or crash on any input; a batch that stops before its last file; a moved public
    function (`validate`, `semantic_errors`, `canonical_set_hash`, `unknown_keywords`, `type_ok`)
    whose behaviour or signature changed; a schema keyword it does not implement silently ignored.
  - **`tools/validate_records.py`**, stdlib only, Python ≥ 3.11:
    - It holds the keyword whitelist, `validate`, `canonical_set_hash` and `semantic_errors`, moved
      from the test script with their behaviour unchanged. Keep those four public names and their
      signatures, because the game repositories' helpers import them.
    - It finds the schemas in `formats/` beside its own parent directory (`<root>/tools/` next to
      `<root>/formats/`). So a consumer that fetches `tools/validate_records.py` and
      `formats/*.schema.json` at a pinned commit, keeping that layout, can run it.
    - It refuses to use a schema with a keyword it does not implement, and says which keyword.
    - It adds a library function `validate_document(doc) -> list[str]`. That function picks the
      schema by the document's `schema` field and applies the schema and the semantic rules. A
      missing or unknown `schema` is an error.
  - **The command line:** `python3 tools/validate_records.py <file.json>…`. For each file it prints
    either `ok: <path>` or one line per error, `<path>: <error>`. It exits 0 when every file is
    valid and 1 otherwise. A file that is not JSON, or has no `schema` or an unknown one, is an
    error for that file, not a crash.
  - **`tests/formats/check_examples.py`** imports the validator's functions instead of defining
    them. It keeps the example and claim-status checks, its output and its exit codes.
  - **`formats/README.md`** says how a game repository uses the validator: list it in
    `archaeology.json`'s `uses`, fetch `tools/validate_records.py` with `formats/*.schema.json` at
    the pinned commit, and never copy or edit it. Update the README's "The validator" section and
    its sentence about the rules being "copied, until a second consumer moves it here".
  - **CI:** one step runs `python3 tools/validate_records.py formats/examples/valid/*.json`.
  - **Not in scope:**
    - any change to a schema, an example or `expected-errors.json`;
    - a new rule, except the one the owner authorized on 2026-10-04 (U23): a record file with a
      duplicate key, at any depth, is invalid, even when the values agree;
    - `formats-v1` (the tag stays where it is);
    - the game repositories' migration, filed in each repository when this merges;
    - `register_artifact.py`.

- **Hazards**:
  - **Changing behaviour while moving code.** A rule that becomes looser or stricter changes which
    records are valid in three repositories. Move the functions verbatim and change only what the
    move requires.
  - **Renaming or re-signing `validate`, `semantic_errors` or `canonical_set_hash`.** It breaks the
    consumers' `ga.py` silently at their next pin bump.
  - **Locating schemas from the working directory instead of the script's path.** Done-when 4
    exists to catch it.
  - **A crash on bad input.** A traceback exits 1 too, so Done-when 5 checks the output, not only
    the code.
