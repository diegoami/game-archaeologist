# T04 The research protocol: researcher brief, research review, promotion (A3)

- **Kind**: architecture
- **Issue**: #11 · **Branch**: `task/T04-research-protocol` · **Merge after**: T02
- **Implementer**: claude (opus, the main session) · **Reviewer**: opencode (`luna`); never the implementer's family
- **Why**: Y2 (the first blind research task) and Y3 (its research review) need the brief blocks that
  turn a research contract into a cold agent's instructions. A6 and every Isle Wars experiment reuse
  them. Research kinds stay in this repo's method until the toy and Isle Wars repos have used them
  (ADR-002); then they go upstream.
- **Evidence** (pasted; the accepted text is in `docs/phase0/` and the ADRs):
  - 03 §1, roles:
    - Researcher: "one bounded question or experiment: runs it, pushes raw evidence **before** writing
      interpretation, drafts a finding with status `proposed`". Must not "promote its own finding;
      edit `spec/`; widen the question; report an inference as an observation". Default: a Claude
      agent (Sonnet); OpenCode only for mechanical sweeps.
    - Research reviewer: "attempts to falsify: identity, reproduction of selected runs, alternative
      explanations, scope". Must not "accept prose without raw evidence; rerun only the runs the
      researcher picked". Never the researcher's family where possible.
  - 03 §2.2: the research and research-review extensions; "Its Done-when lines are about **records,
    not conclusions**".
  - 03 §6.2: gates 0–7 (tree and record identity; artifact identity; environment identity;
    reproduction of runs **the reviewer selects**; raw vs interpretation; ≥2 alternatives; intervention;
    scope), and the **two-axis verdict**: line 2 the record verdict (`approve | approve after named
    fixes | rework | user decision`), line 3 the claim outcome (`supported | supported, narrowed: … |
    inconclusive | refuted`). "A refuted or inconclusive finding with a sound record is approved and
    merged."
  - 03 §6.3, promotion: "After merge, the main session … updates `spec/<area>.md` … a promotion commit on
    `main` with the reason … no PR."
  - 03 §6.5, the defect classes and their routes; ADR-008.
  - 06 §10, blindness for toy research: the researcher "never runs with the owner's own `gh` login …
    either in a cloud session whose GitHub access is limited to `toy-archaeology`, or as an OpenCode
    run with a fine-grained token for that repo alone (needs H2's env allowlist)".
  - `review.mjs` (harness at 74e53ae) reads line 1 as the header, line 2 as the verdict, and the last
    line as the repeated verdict. Line 3 is free, so it can carry the claim outcome.
  - harness_imperial#19 and #24: a review accounts for every Done-when line, and every line is runnable
    by a read-only reviewer.
- **Owns**: `method/**`
- **Scope**:
  - **`method/research-protocol.md`**:
    1. who runs a research task, and with which credentials;
    2. the researcher brief block, appended to the pasted research task file;
    3. the research-review brief block, with the gates, the two-axis verdict and the DW lines;
    4. the promotion procedure;
    5. the defect routing;
    6. the blindness procedure for toy research.
  - **`method/examples/planted/`**: a fabricated experiment with a finding that has planted defects.
    It is clearly marked as fabricated, and its run records are valid `run/1`. It exists to calibrate
    research reviewers. The answer key is **not** in the repository: its sha256 is
    `169be21cbd7cebca7c1acc3d0285309df88b22d4a26fa8f9cdbc2ea2714db5ac`. The main session posts the key
    on the PR after the review verdict, and the reviewer's catches are scored against it.
  - **Not in scope**: changes to `review.mjs` or any harness file (upstream later, ADR-002); the
    record validator (#10); Y2's contract itself.
- **Decisions**:
  - the researcher's default credentials path for toy research;
  - which reviewer runs research reviews (family rule against a Claude researcher);
  - how the claim outcome line is parsed (it is not, by the harness).
- **Escalate**: anything needing a harness change now.
- **Done when**:
  1. `method/research-protocol.md` contains the researcher block and the research-review block as
     fenced `text` blocks:
     `grep -c '^```text' method/research-protocol.md` ≥ 2. The review block names gates 0–7 and both
     verdict lines.
  2. Each fabricated run record validates against `run/1`:
     `python3 -c "import sys,json;sys.path.insert(0,'tests/formats');from check_examples import validate;s=json.load(open('formats/run-1.schema.json'));import glob;[print(f, validate(json.load(open(f)),s) or 'ok') for f in sorted(glob.glob('method/examples/planted/runs/*/*.json'))]"`
     prints `ok` for every file.
  3. **The calibration**: the reviewer applies the review block from the PR's
     `method/research-protocol.md` to `method/examples/planted/`, without the key, as if reviewing that
     finding. It writes the result in its PR comment as "Planted case: <verdict line 2> / <outcome line
     3>", then one line per defect found, naming the gate. The main session then posts the key; the key's
     sha256 must equal the hash above. **At least the gate-5 confound must be found.** If it is not, the
     review block is reworked, not the key.
  4. Every relative link resolves (`python3 tools/check_links.py`), and CI is green.
- **Hazards**:
  - writing the planted defects into the protocol's own examples, which would teach the key;
  - a review block that the harness reader cannot parse (line 1 header, line 2 verdict, last line
    verdict);
  - drifting from 03 §6.2's gates (transcribe them; do not invent new ones).
